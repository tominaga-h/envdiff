# envdiff

`.env` 系ファイル 2 つを **環境変数ごとに** 比較する CLI ツール。

[English README](../README.md)

通常の `diff` は行単位で比較するため、コメントや空行、記述順の違いがノイズとして
差分に現れ、本当に知りたい「どの環境変数が違うのか」が埋もれてしまう。envdiff は
ファイルを環境変数の集合として解釈し、キー単位で比較する。

## インストール

### ビルド済みバイナリをダウンロードする

各[リリース](https://github.com/tominaga-h/envdiff/releases)にビルド済みバイナリを添付している。
Rust ツールチェインは不要。

| OS | アーキテクチャ | アセット |
| --- | --- | --- |
| macOS | x86_64 | `envdiff-x86_64-apple-darwin.tar.gz` |
| macOS | aarch64（Apple Silicon） | `envdiff-aarch64-apple-darwin.tar.gz` |
| Linux | x86_64 | `envdiff-x86_64-unknown-linux-gnu.tar.gz` |
| Linux | aarch64 | `envdiff-aarch64-unknown-linux-gnu.tar.gz` |
| Windows | x86_64 | `envdiff-x86_64-pc-windows-msvc.zip` |
| Windows | aarch64 | `envdiff-aarch64-pc-windows-msvc.zip` |

macOS と Linux では、自分の環境に合うアセットをダウンロードして展開し、`PATH` の通った
場所に置く：

```sh
curl -sSfL https://github.com/tominaga-h/envdiff/releases/latest/download/envdiff-aarch64-apple-darwin.tar.gz | tar xz
sudo mv envdiff /usr/local/bin/
```

macOS では、コード署名をしていないため Gatekeeper にブロックされることがある。その場合は
quarantine 属性を外す：

```sh
xattr -d com.apple.quarantine /usr/local/bin/envdiff
```

Windows では `.zip` を展開し、`envdiff.exe` を `PATH` の通ったディレクトリに置く。

### ソースからビルドする

```sh
cargo install --path .
```

Rust 1.85 以降が必要（2024 edition）。

## 使い方

```
envdiff <A> <B> [OPTIONS]
```

`A` と `B` は単に第 1・第 2 引数であり、出力の A 列・B 列に対応するだけ。どちらかを
「基準」として扱うことはなく、ツールがユーザーの意図を推測することもない。

| オプション | 説明 |
| --- | --- |
| `--all` | 差分のない変数（`same`）も出力に含める |
| `--json` | JSON 形式で出力する |

`--all`（表示範囲）と `--json`（出力形式）は直交する。組み合わせて使え、互いの
意味を変えない。

## 終了コード

`diff(1)` の慣習に従う。`diff` を置き換えても CI が壊れない。

| コード | 意味 |
| --- | --- |
| `0` | 差分なし |
| `1` | 差分あり |
| `2` | エラー（パースエラー、ファイル読み込み失敗、引数不正） |

**エラーを 1 ではなく 2 にしているのは意図的。** 1 にすると「正常に動作して差分を
見つけた」と「ファイルを読めなかった」が呼び出し側から区別できない。パースエラーな
のにログに「差分あり」と出れば、担当者は存在しない差分を探すことになる。

おかげで乖離チェックが一行で書ける。

```sh
envdiff .env.example .env   # 乖離していれば exit 1
```

## 分類

各キーは必ず次の 4 状態のいずれかに分類される。

| STATUS | 意味 |
| --- | --- |
| `changed` | 両方に存在し、値が異なる |
| `only in A` | A にのみ存在 |
| `only in B` | B にのみ存在 |
| `same` | 両方に存在し、値も同じ |

`same` はデフォルトでは出力しない。差分ツールは差分だけを吐くべきで、100 個中 3 個
違うときに 97 行のノイズを読ませない。`--all` で含められる。

`only in A` と `only in B` を区別するのは、`.env.example` と `.env` を比べる典型
ケースで、この 2 つの意味がまったく違うため。example にあって手元にない = 設定漏れ、
手元にあって example にない = 書き忘れか不要な残骸。一括りにすると、このツールの
一番の使いどころで判断材料を潰すことになる。

## JSON 出力

```console
$ envdiff --json .env .env.example
{
  "files": { "a": ".env", "b": ".env.example" },
  "summary": { "total": 3, "changed": 1, "only_in_a": 1, "only_in_b": 1, "same": 0 },
  "diffs": [
    { "key": "PORT",    "status": "changed",   "a": "3000", "b": "8000" },
    { "key": "APP_ENV", "status": "only_in_a", "a": "1",    "b": null },
    { "key": "DEBUG",   "status": "only_in_b", "a": null,   "b": "true" }
  ]
}
```

- キーの不在は `null`、値が空文字は `""`。この 2 つは型で区別される。
- `diffs[].a` / `.b` のキー名は `a` / `b` 固定でファイル名にしない。ファイル名を
  キーにすると入力によって JSON の形が変わり、`jq` のクエリが書けなくなるため。
  実ファイル名は `files` に入る。
- `summary.total` は差分の数。`same` は差分ではないので含まない。

envdiff は差分の重要度を判定しない（「これは設定漏れだから危険」といった主張はしない）。
そのため「`only_in_a` だけを失敗にしたい」といったニーズはユーザー側で解決する。

```sh
envdiff --json .env.example .env | jq '.diffs[] | select(.status == "only_in_a")'
```

これが書けるからこそ、本体に `--only-missing` のようなフラグを増やさずに済む。
**`--json` は単一責務を守るための逃し弁である。**

## パース仕様

`.env` に正式な仕様は存在しないため、envdiff は独自の最小仕様を定めてそれに従う。

### 判断の基準となる一文

> **envdiff は「何が書いてあるか」を比べるツールである。**

「実行時に最終的に何がセットされるか」を比べるツールではない。以下の判断はすべて
この一文から導かれる。

### クォートは剥がす

`PORT=3000` と `PORT="3000"` は **`same`**。dotenv がこのファイルを読み込めば両者
は等しく `PORT=3000` になる。クォートは値の入れ物であって値ではない。これを
`changed` と報告するのは、ユーザーが除きたがっているノイズそのもの。

`"..."` 内のエスケープは `\n` `\r` `\t` `\\` `\"` のみ解釈する。`'...'` は一切
解釈しない（シェルと同じ規則）。

剥がすのは、値の**先頭**がクォートで始まり**末尾**で閉じている場合のみ。したがって
`KEY=foo"bar"` や `JSON={"k": "v"}` は素通しする — そのクォートは値を囲んでいない。
dotenv が読めるファイルは envdiff も読めるべきである。

### 変数展開は行わない

`API_URL=${BASE_URL}/api/v1` と `API_URL=https://example.com/api/v1` は
**`changed`**。`${` は単なる文字。

展開はツールを実行環境に依存させる。`${BASE_URL}` の `BASE_URL` がファイル内にない
とき、シェル環境から取るのか空にするのかエラーにするのか、どれを選んでも「実行環境に
よって差分の結果が変わる」。CI と手元で違う答えを出す比較ツールは信用されない。

また展開は情報を捨てる。上の例は「片方はリファクタされ、片方はハードコードのまま」
という、人間が知るべき差分である。展開するとこれを `same` として握り潰す。

`--expand` のようなオプトインも設けない。オプションであっても環境依存の結果を返す
口を持つことになるため。

### 複数行の値を読める

```env
PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----
MIIEpAIBAAKCAQEA...
-----END RSA PRIVATE KEY-----"
```

Rails の `master.key`、Firebase のサービスアカウント、GCP 認証情報など実在する形式。
クォートが閉じないまま行が終わった場合、閉じるまで次行以降を値として読み続ける。

ファイル末尾までクォートが閉じなかった場合はパースエラー。メッセージはクォートの
**開始行**を指す。

```
error: .env:12: quote opened here is never closed (reached end of file)
```

「EOF で閉じていません」だけでは、200 行のファイルのどこが原因か探すことになる。

### 重複キーは警告する

後勝ちで値を採用し、stderr に警告を出す。

```
warning: .env:14: duplicate key 'DB_HOST' (overrides value from line 9)
```

重複キーはほぼ確実にバグである（書いた人は上の行が効くと思っている）。黙って後勝ちで
処理すると、envdiff が「差分なし」と報告しながら時限爆弾を見逃す。一方でパースエラー
にもしない — `.env` 側の重複のせいで比較全体が失敗すると、ユーザーは本当に知りたかった
差分にたどり着けない。

警告は stdout（機械が読む結果）ではなく stderr（人間が読む注意）に出るため、パイプに
影響しない。終了コードにも影響しない。警告は警告であって失敗ではない。

### その他の規則

| 入力 | 結果 |
| --- | --- |
| `KEY=VALUE` | `=` の**最初の出現**で分割する（値に `=` を含められる） |
| `export KEY=VALUE` | `export` を剥がす |
| `# コメント` | 無視する。ただしクォート内の `#` はコメントではない |
| `KEY=` | 値が空文字の変数として**存在する**（「未設定」ではない） |
| `KEY`（`=` なし） | **パースエラー** — 束縛が存在せず、何を意味する行か決めようがない |
| `=VALUE` | **パースエラー** — 束縛される先がない |

不正な行に出会ったらその時点でエラー終了する（exit 2）。読み飛ばして続行しない。
黙ってスキップすると「変数が片方にない」と誤報告し、ユーザーは実ファイルではなく
envdiff のバグを疑うことになる。比較ツールは、読めなかったものを差分として報告しては
いけない。

### 出力順序

キーは**ファイルに書かれている順**に並ぶ。アルファベット順にはしない。A に存在する
キーを A の行番号順に並べ、その後ろに `only in B` のキーを B の行番号順で続ける。

ユーザーは差分を見た後、実ファイルを開いて直す。書かれている順に並んでいれば出力と
ファイルを上から突き合わせられる。アルファベット順は「ファイルのどこを見ればいいか」
の情報を捨てる。

## 強調と色

`changed` 行では、値のうち **実際に異なる部分だけ** が太字になり、色が付く。A 側は赤、
B 側は緑。共通部分は無加工で出る。

```
DATABASE_URL │ postgres://localhost:5432/db │ postgres://db.prod:5432/db
                          ~~~~~~~~~                      ~~~~~~~
                          赤 + 太字                       緑 + 太字
```

STATUS 列は「その変数が変わった」ことを言う。強調は「値のどこが変わったか」を言う。
40 文字の `DATABASE_URL` のうちホスト名だけが違うとき、それがまさに知りたい情報である。

対象は `changed` 行だけ。`only in A` / `only in B` は片側にキーが存在せず比較対象が
ないため、「値の中のどこが変わったか」が定義できない。キーごと存在しないのであり、
それは STATUS 列が言っている。`same` 行は定義上差分がない。

太字と色はまったく同じ文字に乗るため、色は太字が既に言っていること以上を言わない。
色は A/B の区別を読みやすくするためにある。それでも両方を乗せるのは、**消える条件が
違う** ため。パイプや `NO_COLOR` では色が、bold ウェイトを持たないフォントでは太字が、
赤緑の色覚特性では色が失われる。どれか一つが残れば「どの部分が変わったか」は読める。

`NO_COLOR` が設定されている場合、および出力先が TTY でない場合は無効化する。判定は
**stdout** に対して行い、stderr とは独立している。`--json` は ANSI を一切含まない。

stderr の warning / error にも色を付ける。ここは「注意を引く」ことが目的であり、色が
唯一の役割を果たすため。判定は stderr に対して行う（v1.0.0 から変更なし）。
