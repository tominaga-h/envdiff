# Implementation Plan: envdiff

SPEC.md（§番号はすべて SPEC.md を指す）に基づく実装計画。

## Overview

`.env` 系ファイル 2 つを環境変数のキー単位で比較する CLI を、単一クレートの Rust バイナリとして実装する。
価値の中心は自前パーサ（§4）であり、比較ロジック（§5）と出力（§6）はその上に薄く載る。

## Architecture Decisions

### AD-1: モジュール構成

```
src/
  main.rs      引数パース（clap）、ファイル読み込み、終了コード決定
  parser.rs    §4 — 文字列 → Vec<(key, value)> + 重複警告
  diff.rs      §5 — 2 つのパース結果 → Vec<Diff>
  render.rs    §6.1 — テーブル + サマリ + 凡例
  json.rs      §6.2 — serde 構造体
```

**根拠:** §8 のテスト戦略が「パーサのユニットテスト」「比較ロジックのユニットテスト」「CLI 統合テスト」の
3 層に分かれている。この境界をそのままモジュール境界にすると、テストがモジュールに素直に対応する。
特に `diff.rs` は「パース済みの構造体を入力とするため、ファイル I/O は不要」（§8.2）であり、
I/O から切り離すことが仕様上の要請になっている。

### AD-2: パーサは行分割せず文字スキャンで実装する

`lines()` で分割してから処理する素朴な実装は §4.6（複数行の値）で破綻する。クォートが開いたまま
行末に達したら次行を値として読み続ける必要があり、行の境界が値の内部に入り込む。

したがってパーサは入力全体を 1 つの文字ストリームとして走査し、行番号は改行を数えて自前で追う。
§4.6 のエラーメッセージは「クォートの**開始行**」を指す必要があるため、
クォート開始時点の行番号を保持する。

### AD-3: パース結果はキー → (値, 行番号) を保持し、出力は行番号順に並べる

§4.7 の重複キーは「後勝ち + 警告（前の行番号を含む）」。警告文 `duplicate key 'DB_HOST' (overrides value from line 9)`
は**前回出現の行番号**を要求するため、キー → (値, 行番号) を保持する必要がある。
`HashMap<String, (String, usize)>` に挿入し、既存エントリがあれば警告を出して上書きする。

**出力順序は行番号の昇順**（＝ファイルに書かれている順）とする。ユーザーが目のファイルと
出力を突き合わせられるため。ソート順は「ファイルのどこを見ればいいか」の情報を捨てる。

**重複キーの行番号は「後勝ちした行」を採る。** §4.7 で採用される値がその行のものであり、
値と行番号が食い違うと、ユーザーが出力の行番号を頼りにファイルを開いたとき別の値を見ることになる。

**複数行の値（§4.6）の行番号は「開始行」を採る。** `KEY=` が書かれている行であり、
ユーザーがその変数を探すときに開く行。値の終端行ではない。

**A と B で順序が競合する場合:** 行番号は A と B で独立した空間にある。次の規則で 1 つの順序に畳む。

1. **A に存在するキー**（`changed` / `same` / `only_in_a`）を、**A の行番号**の昇順に並べる
2. **A に存在しないキー**（`only_in_b`）を、**B の行番号**の昇順に、1 の後ろに続ける

**根拠:** `only_in_b` のキーは A の中に位置を持たないため、A の順序列に挿入する場所が定義できない。
また §2 で「A と B に非対称な意味付けはしない」とあるが、これは*意味*の非対称性の話であり、
出力の列順が A → B である以上（§6.1）、順序の基準を A に置くことは既存の非対称性と一貫している。

> 確認済み。SPEC §5.3 に反映（正典は SPEC 側）。

### AD-4: パース警告は返り値として返し、出力は呼び出し側が行う

パーサが直接 `eprintln!` すると、ユニットテスト（§8.1「重複キーは後勝ち + 警告」）が
標準エラーのキャプチャを必要とし、テストが不必要に重くなる。
パーサは `ParseOutput { vars, warnings: Vec<Warning> }` を返し、`main.rs` が stderr へ書く。

### AD-5: §4.8「不正な行」の定義（確定済み）

SPEC は「上記のいずれにも当てはまらない行」としか書いておらず判定基準がなかったため確認し、
次の方針が確定した:

- `KEY=` は環境変数として**認知する**（値が空文字。§5.2 と一致）
- `KEY` のみ（`=` なし）は環境変数として**認知しない** → パースエラーで即停止
- `export` プレフィックスを剥がした後に判定する
- キーが空（`=VALUE`）もパースエラー（束縛される先がない）

**根拠:** `.env` の行は「キーが値に束縛される」ことを意味する。`=` がなければ束縛が存在せず、
どんな変数を意味するのか決めようがない。黙って読み飛ばすことは §4.8 が明示的に禁じている。

### AD-7: §4.4「値を囲む」の定義（確定済み）

SPEC §4.4 は「値を囲む」クォートを剥がすとしか書いておらず、囲めていない場合の
判定基準がなかったため確認し、次の方針が確定した:

- 剥がすのは、値の**先頭**がクォートで始まり、値の**末尾**で閉じている場合のみ
- `KEY=foo"bar"` / `KEY={"k": "v"}` は**素通し**（先頭が非クォート＝囲んでいない）
- `KEY="foo"bar` は**パースエラー**（先頭がクォートなのに囲めていない）

**素通しの根拠:** 先頭が `f` や `{` である以上、そのクォートは値を囲んでいない。
`${` を単なる文字として扱う（§4.5）のと同じく、単なる文字として値に含める。
これをエラーにすると `JSON_FRAGMENT={"k": "v"}` や `MESSAGE=say "hello"` のような、
dotenv が問題なく読めるファイルが比較できなくなる。**dotenv が読めるファイルは
envdiff も読めるべき**（§4.6・§4.7 が同じ原則を根拠にしている）。

**エラーの根拠:** `KEY="foo"bar` は、先頭がクォートであるため読者は「囲んでいる」と
読むが実際には囲めておらず、値が `foo` か `foobar` か実装ごとに割れる。黙ってどちらかに
決めれば、§4.8 が禁じる「読めなかったものを差分として報告する」ことになる。
`foo"bar"` にこの曖昧さはない（先頭が非クォートなら囲むクォートとは読めない）。

**§4.4 への影響:** SPEC に規定がなかったため §4.4 に「値を囲む」の定義を追記した
（Task 3 に含む）。仕様書とコードが食い違ったまま進むと、次に SPEC を読む人が
誤った前提を持つ。

### AD-6: 色は専用クレート（`owo-colors`）を使う

§6.1 の MVP 要件は「stderr の warning / error のみ」に限られるが、将来テーブルへ色を付ける
可能性があると確認できたため、ANSI 直書きではなくクレートを使う。

`owo-colors` を採用する。理由は、`NO_COLOR` と TTY 判定を含む出荷可能な挙動が
`owo_colors::Stream` ベースの API（`if_supports_color`）で完結し、判定ロジックを自前で持たずに済むこと。
`colored` は同等だがグローバル状態を持ち、stdout と stderr で色の可否を独立に判定する
（MVP はまさにこれ — stderr のみ色付き）用途と噛み合わない。

**§7 への影響:** 依存クレート表にない追加であるため、SPEC §7 に 1 行追記する（Task 1 に含める）。
仕様書と Cargo.toml が食い違ったまま進むと、次に SPEC を読む人が誤った前提を持つ。

## Slicing Strategy

垂直スライスの単位は「§4 の 1 仕様項目 = 1 テスト = 1 タスク」ではなく、
**「ユーザーが観測できる 1 つの振る舞い」**とする。ただし Task 2 と Task 6 の間には
「パースできても表示できない」期間が生じる。これは避けられない — 比較ツールは
パーサなしに何も出力できないため、最初の縦串は必然的に Task 2 → 5 → 6 → 7 の 4 タスクにまたがる。

そこで **Task 6 を最小の縦串（`envdiff a b` が動いて exit code を返す）として早めに置き**、
Task 3/4（パーサの難所）はその後に積む。これにより「動くものが早く手に入り、その後で
パーサを深くしていく」順序になる。

## Task 3: パーサ — クォートと複数行の値

**Description:** §4.4 と §4.6 を実装する。パーサの最難所であり、
Task 2 で確定した API の内側を深くする。行分割ではなく文字スキャンで実装する（AD-2）。

§4.3 の「クォート内の `#` はコメントではない」は、Task 2 のコメント処理と本タスクの
クォート処理が同じスキャナ内で協調して初めて成立する。Task 2 では単純に `#` 以降を捨てているため、
本タスクでその判定を修正する。

**Acceptance criteria:**
- [ ] `'...'` と `"..."` を剥がす（`PORT=3000` と `PORT="3000"` が `same`）
- [ ] `"..."` は `\n` `\r` `\t` `\\` `\"` **のみ**をエスケープとして解釈する
- [ ] `'...'` はエスケープを一切解釈しない
- [ ] クォート内の `#` がコメントとして扱われない
- [ ] `${FOO}` を展開せず、単なる文字として扱う
- [ ] クォートが閉じないまま行末に達したら、閉じるまで次行以降を値として読む（`"` `'` 両方）

# Addendum: Phase 4 — changed 行の値の文字単位ハイライト

v1.0.0 リリース後の追加計画。Tasks 1–10 と Checkpoint A–C は完了済みであり、以降は
**この Addendum が現行の計画**である。上の AD-1..AD-7 は引き続き有効で、AD-8..AD-12 を足す。

## Motivation

長い値（`DATABASE_URL` など）が `changed` のとき、テーブルは「A はこれ / B はこれ」を
並べるだけで、**どこが変わったか**は読者が目で突き合わせることになる。
`postgres://user@localhost:5432/db` と `postgres://user@db.prod:5432/db` の差は
ホスト名 1 箇所だが、現状の出力はそれを指し示さない。

これは §6.1 が色を却下した根拠のうち **「STATUS 列に既に書いてあり、色は情報を足していない」に
真正面から答える**唯一の変更である。「どの部分が」は STATUS 列が持っていない情報であり、
重複ではない。

## Architecture Decisions

### AD-8: 強調は**太字**であり、色ではない

§6.1 は色を 3 つの根拠で却下している。太字はそのうち 2 つを**原理的に消す**。

| §6.1 の反論 | 太字での帰結 |
| --- | --- |
| 「STATUS に書いてあり情報を足していない」 | **文字単位ハイライトが答える**（どの部分か、は新情報） |
| 「赤/緑は良し悪しを含意し、§3 に反する」 | **消える。** 太字に valence はなく「ここが違う」しか言わない |
| 「赤緑は色覚特性上もっとも区別しにくい」 | **消える。** 太字は色相ではなく、P 型 / D 型 / 全色盲で等しく読める |

**根拠:** 3 つの反論すべてに答えが付く唯一の案である。青/黄 等の非 valence な配色は
2 番目にしか答えず、「なぜ 2 色必要か」（A/B の区別は既に列位置とヘッダーが担っている）に
答えられない。太字は問い自体を消す。

**A/B を区別しないことは欠点ではない。** A/B の区別は列の位置とヘッダー（`.env (A)` /
`.env.example (B)`）が既に担っており、ハイライトに求められるのは「値のどの部分が変わったか」
だけである。強調が 1 種類で足りる。

**§6.1 の「テーブルに色を付けない」は撤回しない。** 太字は色ではないため、この一文は
そのまま生き残る。SPEC への変更は**否定ではなく追記**である（Task 11）。

**既知の弱み（許容する）:** SGR 1 の描画は端末依存で、bold ウェイトを持たないフォントでは
無視されるか明るい色に化けることがある。ただしハイライトは**付加情報**であり、意味は
STATUS 列と列位置が担っている。太字が出なくても情報は失われず、手掛かりが減るだけである
（§6.1 が色に対して「唯一の役割を果たす」ことを要求したのは stderr 側の話であり、ここは該当しない）。

### AD-9: 強調対象は `changed` 行の A/B 値セルのみ

`only_in_a` / `only_in_b` は比較対象が存在せず、`same` は定義上差分がない。
`Diff.a` と `Diff.b` が**両方 `Some`** かつ `status == Changed` のときだけ強調が意味を持つ。

**根拠:** `only in B` の行で B の値を丸ごと太字にすると「値の中のどこかが変わった」という
誤読を招く。実際にはキーごと存在しないのであり、それは STATUS 列が言っている。

### AD-10: 位置合わせは `similar` の**文字単位** Myers に任せる（自前の index 走査は不可）

先頭から index を揃えて 1 文字ずつ比較する素朴な実装は、**挿入・削除が入った時点で破綻する**。

```
A: postgres://localhost:5432/db
B: postgres://db.prod:5432/db
```

`localhost`(9) と `db.prod`(7) は長さが違うため、以降の `:5432/db` は 2 文字ずれたまま
比較され続け、**両者に同一で存在するのに全部「差分」と判定される**。結果、値の大半が
太字になり「どこが違うか」を示す目的が消える。共通部分列の検出には LCS が要る。

`similar` を採用する。`TextDiff::from_chars(a, b)` が文字粒度の Myers 差分を返し、
`iter_all_changes()` が `Equal` / `Delete` / `Insert` のタグ付きで列挙する。
トークナイズの設計判断（何で区切るか）は**発生しない** — 文字を見るため。

**§7 への影響:** 依存表にない追加であるため SPEC §7 に 1 行追記する（Task 11 に含む）。

### AD-11: ハイライトは `render.rs` に置く。`diff.rs` には入れない

`diff.rs` は §8.2 が「パース済みの構造体を入力とし、I/O を含まない」と定めた層であり、
その責務は §5.1 の 4 分類である。「値のどの範囲が光るか」は**表示の関心事**である。

**根拠:** `--json` は §6.2 で「切り詰め・折り返し・色を一切適用しない」と決めている。
`Diff` にハイライト情報を持たせると `json.rs` がそれを無視する構造になり、
「`diff.rs` は表示に関与しない」という既存の境界が滲む。`render.rs` に閉じれば
`json.rs` は現状のまま 1 行も変わらない（Task 13 の検証項目）。

### AD-12: §8.4 を守るため「**範囲を決める純粋関数**」と「ANSI を付ける処理」を分ける

§8.4 は「テーブル出力の文字列一致テストを書かない」— 見た目は調整可能であるべきだから。
一方でハイライト**範囲**の計算は、見た目ではなくロジックであり、回帰したら気付けない。

したがって次の 2 層に割る。

| 層 | テストするか | 理由 |
| --- | --- | --- |
| 「A/B の値 → 強調する範囲（`Vec<Segment>`）」を返す純粋関数 | **する** | 見た目ではなくロジック。§8.4 の対象外 |
| その範囲に ANSI を被せてセル文字列にする処理 | **しない** | まさに §8.4 が固定を禁じた「見た目」 |

**根拠:** この線引きにより §8.4 を破らずにテスト可能性を確保できる。テストは
「`3000` / `8000` で強調されるのは先頭 1 文字」のように**範囲**を主張し、
ANSI エスケープの有無や太字の出方には一切触れない。
